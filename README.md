# Lima UI

## 🚀 Структура проекта

Этот проект создан с использованием:

- **Node.js >= 22.15.0**
- **Vite** — сборщик для быстрой разработки и сборки.
- **Solid.js** — фреймворк для создания пользовательских интерфейсов.
- **Astro** — инструмент для генерации статических сайтов.
- **TypeScript** — для статической типизации и повышения надежности кода.

### Дополнительные библиотеки

- **Floating UI** (@floating-ui/dom 1.6.13, solid-floating-ui 0.3.1) — позиционирование элементов
- **Solid DND** (@thisbeyond/solid-dnd 0.7.5) — drag and drop функциональность

## Подготовка к запуску проекта

- Клонируем репозиторий.
- Устанавливаем зависимости при помощи команды: `npm install`.
- Клонируем, устанавливаем и запускаем [серверный репозиторий](https://github.com/Terbiy/svernik).

## 🧞 Команды

Все команды выполняются из корневой директории проекта через терминал:

| Команда | Действие |
| :-- | :-- |
| `npm install` | Устанавливает зависимости |
| `npm run dev` | Запускает локальный сервер разработки на `localhost:4321` |
| `npm run build` | Сборка вашего сайта для продакшена в папку `./dist/` |
| `npm start` | Запускает продакшен-сервер из папки `dist` |
| `npm run preview` | Запускает локальный сервер для предпросмотра продакшен-сборки |
| `npm run astro` | Запускает интерфейс командной строки Astro |
| `npm test` | Запускает все тесты на всех устройствах (desktop, tablet, mobile) |

**Примеры использования:**

```bash
# Запуск всех тестов на всех устройствах (игнорирует @broken)
npm test

# Показать справку
npm test -- --help

# Запуск тестов только для десктопа и планшета
npm test -- --desktop --tablet

# Запуск только сломанных тестов
npm test -- --broken

# Запуск только текущих тестов (с тегом @current)
npm test -- --current

# Комбинирование флагов: запуск текущих тестов в отладочном режиме
npm test -- --current --debug
```

## Доступность

На данный момент мы строго не соблюдаем все требования WCAG о доступности, однако:

- Наши дизайнеры уже стараются соблюдать требования о контрастности и читаемости
- Команда разработчиков старается не делать грубых нарушений требований WCAG
- Соблюдаем правильную вложенность интерактивных элементов (например не размещать кнопку внутри кнопки)
- Соблюдаем правильную вложенность семантических элементов (например не размещаем div внутри label, или div внутри span)
- По возможности реализовываем простую функциональность или атрибуты, повышающие доступность (например добавлять aria-label на кнопки без текста и т.е не требующие больших трудозатрат)
- Стараемся не нарушать семантику и использовать по максимуму нативные браузерные элементы (input, textarea, button и тд)
- Правильно использовать атрибуты у нативных элементов, которые могут повлиять на доступность (например disabled у button)
- Следим за наличием фокуса у интерактивных элементов и его стилизацией, а также правильным порядком фокуса
- Никогда не нарушаем W3С валидацию и проверяем компоненты на валидность
- При разработке стараемся применять популярные паттерны проектирования интерфейса из APG Patterns
- Поддерживаем зум и используем относительные единицы измерения

Все эти меры позволят нашему продукту в будущем гораздо легче пройти модернизацию для полноценной доступности.

На данный момент мы не делаем для доступности:

- Полноценную клавиатурную навигацию (включающую стрелки и горячие клавиши по рекомендации WCAG)
- Целенаправленно не используем логические CSS свойства (padding-inline и т.д.)
- Не реализовываем motion reduce

# Руководство по написанию CSS

## Общие принципы

- Главный и основной принцип стилизации на нашем проекте, максимально избегать хардкодинга размеров. Компоненты должны быть максимально гибкими и резиновыми, быть готовыми принимать любое количество контента, которое предполагает компонент, и при этом не ломаться визуально.
- Мы стараемся называть классы абстрактно, чтобы компонент был максимально универсальным. Но при этом чтобы было понятно какую функцию выполняет или какие элементы в себе ожидает та или иная обертка.
- Мы стараемся избегать абсолютных единиц измерения: `px`, `cm`, `pt` и других.
- Мы стараемся использовать только относительные: `%`, `rem`, `vh`, `vw`, но пока что избегаем `em`.
- Используйте **только `rem`** для фиксированных размеров. Использование `px` **запрещено** и контролируется через конфигурацию `stylelint`. В проекте для тега `html` установлен базовый шрифт **10px** поэтому `1rem = 10px` для удобства вычисления `rem` при разработке.
- Установите плагин `stylelint` для вашей IDE, чтобы избежать нарушений кодстайла.
- Старайтесь минимизировать вложенность селекторов, чтобы избежать проблем с производительностью и переопределением стилей.
- Используйте **BEM** (подробнее о нашем подходе далее)
- **Использование `!important` запрещено.**
- Используйте `flexbox` и `grid` для построения макетов вместо `float` или `position` (за исключением специфических случаев).

  - `organisms/` — крупные компоненты (`header`, `sidebar`, `toolsPanel` и т. д.).
  - `pages/` — страницы приложения и структура для сторисов компонентов в Сторибуке.

## CSS-переменные

- В проекте вместо цветов `HEX` и `RGB` используются **CSS-переменные**.
- Исключения: градиенты и тени, в редких случаях.
- Применяется **система брендированных цветов**:
  - Числовое отображение яркости конкретного цвета: `var(--primary-100)` … `var(--primary-900)` (с шагом `100`, в редких случаях `50`).
  - Отдельные переменные для текста с префиксом `text`, например `var(--text-neutral-100)`.
- **Новые переменные добавляют только дизайнеры**. Разработчики используют только те переменные, которые есть в **Figma**.
- **Полный список переменных доступен в `src/layouts/main.css`**.

Пример использования переменных:

```css
.button {
  background-color: var(--primary-500);
  color: var(--text-neutral-100);
  font-size: 1rem;
}
```

## Единицы измерения

- Используйте **только `rem`** для размеров.
- Используйте `vw`, `vh` только в случаях, когда это действительно необходимо.

- Все классы должны быть в **camelCase**.
- Используйте `shorthand`-свойства только когда это уместно.
- Объединяйте похожие свойства.

Пример:

```css

  display: flex;
  flex-direction: column;
  padding: 1rem;

```

## Подробнее о БЭМ

Мы применяем БЭМ, чтобы изолировать стили компонентов друг от друга и изолировать стили размеров/тем внутри компонента друг от друга. Это помогает визуально отделять компоненты друг от друга, понимать, какие теги к какому компоненту относятся, в каком состоянии находится компонент, а также избежать путаницы и многократных переопределений стилей при дебагинге через DevTools. Плюсом еще позволяет ускорить парсинг стилей браузером.

В проекте используется не полноценная методология БЭМ, мы намеренно избегаем некоторых сложных или избыточных подходов, описанных в официальной методологии, потому что считаем, что они или пока нам не требуются или не идеальны изначально по своей задумке.

Основные правила именования по методологии БЭМ делятся на 3 основных части имени:

### 1. Блок

Блок — это корневой тег компонента и именуется стандартно для БЭМ, его имя пишется через camelCase и **полностью повторяет название компонента в tsx** например:

```html
<div class="button"></div>
```

### 2. Модификатор

Модификатор используется для стилизации темы, размера или состояния компонента. Пример модификатора:

```html
<div class="button button_large"></div>
```

Используйте модификаторы только в сочетании с блоком, так как мы решили выбрать именно этот путь для того, чтобы отслеживать состояния компонента в одном месте при просмотре кода через DevTools. Для стилизации вложенных элементов в зависимости от модификатора используйте CSS-каскад. Например:

```html
<div class="button button_large">
  <!-- Модификатор указан у блока, а не у элемента, который мы хотим стилизовать -->
  <span class="button__text"></span>
</div>
```

```css
.button_large .button__text {
  /* Таким каскадом мы дотягиваемся до нужных элементов */
  font-size: 1.25rem;
}
```

### 3. Элемент

Элемент — это любая внутренняя часть компонента, которая не может быть использована отдельно от компонента. В именовании элемента используется имя родительского блока и через два нижних подчеркивания пишется уже имя элемента, например:

```html
<div class="button__text"></div>
<!-- текст до двойного нижнего подчеркивания это имя блока, которому принадлежит элемент, а текст после двойного нижнего подчеркивания это имя элемента-->
```

Элементы могут повторяться внутри компонента несколько раз, но мы рекомендуем подумать может ли этот элемент использоваться в других компонентах в будущем и при необходимости вынести в отдельный компонент и предложить сделать то же самое команде дизайнеров. Но обычно всё деление на компоненты происходит уже на дизайне.

### Популярные ошибки в БЭМе

**Ошибка 1:** Блок получил, помимо класса блока получил еще и класс элемента другого компонента:

```html
<div class="form__button button"></div>
```

**Ошибка 2:** В имени не может быть "двойного названия" элемента:

```html
<div class="form__wrapper__title"></div>
<!-- Использовали дважды нижнее подчеркивание-->
```

Вместо этого нужно делать вложенность так:

```html
<div class="form__titleWrapper">
  <span class="form__title">Text</span>
</div>
```

**Ошибка 3:** У тега не может быть названий сразу двух элементов или блоков:

```html
<!-- два элемента -->
<div class="form__title form__text"></div>
<!-- или два блока -->
<div class="form modalDialog"></div>
```

**Ошибка 4:** Нельзя задавать модификаторы элементам:

```html
<div class="form__title form__title_error"></div>
```

**Ошибка 5:** Нельзя задавать двойной модификатор:

```html
<div class="form form_visibleError_visibleContent"></div>
```

Мы стараемся разрабатывать модификаторы так, чтобы можно было их комбинировать друг с другом или использовать по отдельности, предыдущий пример правильно было бы сделать так:

```html
<div class="form form_visibleError form_visibleContent"></div>
```

Конечно, бывают исключения, например мы не можем скомбинировать два модификатора которые противоречат друг другу, например `form_hidden` и `form_visible`, учитывайте это при разработке логики компонента.

**Ошибка 6:** У тега не может быть названий сразу двух элементов:

```html
<div class="form__title form__text"></div>
```

**Ошибка 7:** Разумеется компонент, может использовать другие компоненты внутри себя. Но это не делает его элементом этого компонента, его стили по-прежнему изолированы и не могут быть переопределены стилями родительского компонента. То есть запрещены такие элементы:

```html
<div class="button">
  <div class="button__text text">
    <!-- Блок одного компонента и элемент другого являются одним тегом, это запрещено -->
    <div class="text__wrapper">Text</div>
  </div>
</div>
```

Вместо этого правильно будет сделать так:

```html
<div class="button">
  <div class="button__text">
    <!-- Разделили элемент родительского компонента и блок вложенного отдельного компонента на отдельные теги, это правильно -->
    <div class="text">
      <div class="text__wrapper">Text</div>
    </div>
  </div>
</div>
```

Обратите внимание, что в этом примере показано, как будет выглядеть, уже собранная разметка в браузере, а не один конкретный tsx-файл. О двух блоках в одном файле читайте в следующей ошибке.

**Ошибка 8:** Не создавайте в одном JSX-файле два блока. Один компонент(tsx файл) может содержать только один блок и только его элементы:

```html
<div class="button">
  <div class="button__text">
    <div class="text">
      <div class="text__wrapper">Text</div>
    </div>
  </div>
</div>
```

Иначе если вы создадите два блока в одном компоненте, вам придется в одном и том же css файле стилизовать два независимых компонента. Вместо этого лучше разделите компоненты на отдельные tsx и css файлы и вызывайте один компонент в другом.

_Исключение_: бывает необходимость иметь два разных блока в одном tsx файле, но при этом эти блоки не могут использоваться отдельно друг для друга, например обертка триггера тултипа и сам тултип. Сделать один из них элементом другого не представляется возможным, потому что тултип рендерится в портале и это нарушало бы БЭМ. Данное правило было сформулировано скорее для компонентов, которые могут и будут использоваться отдельно друг от друга.

**Ошибка 9:** Не стилизуйте каскадом другие компоненты. В файле стилей компонента должны быть только изолированные стили и не должны переопределять стили других компонентов:

```css
.form__button .button {
  font-size: 1.25rem; /* Мы стилизовали в файле стилей компонента form, другой компонент button, это нарушает изоляцию стилей */
}
```

### Cоветы:

**Совет 1:** Если ситуация вынуждает изменить стили вложенного компонента для конкретного места применения компонента, тогда сначала проверьте используете ли вы нужную тему или размер компонента. Если имеющиеся темы и размеры не подходят, то есть только два варианта, либо в дизайне появился новый размер или тема компонента, которая еще не добавлена в код, либо в дизайне допущена ошибка и нужно об этом сообщить команде дизайна.

**Совет 2:** Если появилась необходимость например скрывать какой-то дочерний компонент, используйте этот подход:

```html
<div class="form form_hiddenTitle">
  <div class="form__content">
    <span class="form__titleWrapper">
      <h1 class="title">Text</h1>
    </span>
  </div>
</div>
```

```css
.form_hiddenTitle .form__titleWrapper {
  display: none; /* Это позволит скрыть родительскую обертку вложенного компонента, соответственно и сам вложенный компонент */
}
```

## Темы и размеры компонентов

Каждый компонент в нашем проекте всегда по умолчанию имеет Medium размер и базовую тему Primary. Без темы и размеры компонент не может существовать. Это необходимо для того, чтобы быстро и удобно добавлять новые темы и размеры, а существующие стили сразу выделить в отдельные темы и размеры для понятной структуры кода.

Размеры и темы задаются с помощью класса-модификатора и устанавливаются только на блок компонента (корневой тег компонента), например:

```html
<div class="button button_primary button_large"></div>
```

Посмотреть имеющиеся названия тем и размеров можно в Figma. Чаще всего это:

Темы:

- **primary** — базовая и самая используемая тема компонента на проекте
- **secondary** — дополнительная тема для исключительных случаев
- **tertiary** — еще одна дополнительная тема для исключительных случаев
- ... — дополнительных тем может быть и больше у очень переиспользумых компонентов
- **successful** — тема, означающая одобрительные действия
- **dangerous** — тема, означающая опасные или необратимые действия (например кнопка удаления)

Многие наши компоненты имеют только Primary тему.

Размеры:

- **xs** — extraSmall
- **s** — small
- **m** — medium
- **l** — large
- **xl** — extraLarge

Многие наши компоненты имеют только Medium размер. Верстать стоит только те темы и размеры, которые были отрисованы в **Figma**.

Бывают **встраиваемые** размеры, например mediumEmbedded, на примере `IconButton`, это размер который имеет такой же размер иконки внутри как и у `medium` размера `IconButton`, но имеет меньшие падинги и внешние размеры, чтобы компонент с таким размером можно было встраивать внутрь других `medium` компонентов, например в `Input`.

### Как стоит верстать размеры, темы, типы и дополнительные состояния

Все базовые CSS-свойства размещаются в блоке обычного класса или элемента и не меняются в зависимости от темы или размера:

```css
.button {
  display: flex;
  align-items: center;
}

.button__text {
  white-space: nowrap;
  text-align: left;
}
```

Стили размеров содержат все CSS-свойства, которые могут так или иначе влиять общий размер компонента или его вложенных элементов, например:

- `padding`
- `width`
- `height`
- `border-width`
- `border-radius`
- `font-size`
- `line-height`
- ... и т.д.

```css
.button_large {
  font-size: 1.25rem;
}
```

Стили тем содержат все CSS-свойства, которые могут так или иначе влиять на цвет или визуальный стиль компонента или его вложенных элементов, например:

- `color`
- `background`
- `border-color`
- `font-weight`
- `text-decoration`
- ... и т.д.

Чтобы стилизовать размер или тему отдельных элементов компонентов, используйте CSS-каскад:

```css
.button_large .button__text {
  font-size: 1.25rem;
}

.button_primary .button__text {
  color: var(--text-neutral-100);
}
```

Мы одобряем использование наследования стилей, поэтому если это уместно, то наследуемые стили можно применять просто к модификатору:

```css
.button_large {
  font-size: 1.25rem;
}

.button_primary {
  color: var(--text-neutral-100);
}
```

Обратите внимание, что нельзя смешивать темы и размеры в одном CSS-правиле, например так:

```css
.button_large.button_primary {
  font-size: 1.25rem;
}
```

Дополнительные типы, которыми нужно управлять, стилизуются отдельными модификаторами, если предполагается несколько разновидностей для одного компонента:

```css
.button_leftTextAlign .button__text {
  text-align: left;
}

.button_centerTextAlign .button__text {
  text-align: center;
}
```

Или например если предполагается несколько состояний:

```css
.button_iconHidden .button__icon {
  display: none;
}
```

Еще один пример:

```css
.accordion__content {
  display: none;
}

.accordion_open .accordion__content {
  display: block;
}
```

На данный момент `Disabled` состояние стилизуется отдельным модификатором, применятся вместе в модификатор темы и частично переопределяет стили темы:

```html
<div class="button button_primary button_disabled"></div>
```

```css
.button_primary {
  color: var(--text-neutral-500);
}

.button_disabled {
  color: var(--text-neutral-300);
}
```

## Медиа-запросы

Мы следуем подходу `Desktop-first` т.е. Когда десктопные стили стилизуют планшетную и мобильную версии, если они не переопределяются медиа-запросами. Наши дизайнеры и разработчики стараются создавать такой интерфейс, чтобы в десктопе и мобильной версии он был максимально схож и сохранял свой UX, позволяя пользователю использовать свои привычки в продукте вне зависимости, каким устройством он пользуется. То есть мы стараемся избегать медиа-запросов. Это делает код чище, легче в поддержке, предсказуемей и безопасней.

Мы используем современный синтаксис для медиа запросов, например:

```css
@media (width <= 767px) {
  .button {
    height: 3rem;
  }
}
```

Мы используем следующие брейкпойнты:

- 767px и меньше — мобильная версия
- 768px - 1023px — планшетная версия
- 1024px и больше — десктопная версия

Разумеется, если устройство определенного типа имеет размеры, не попадающие под его категорию, то оно использует стили для той версии, под которую подходит именно его размер экрана. Например, планшет с экраном 1400px, будет использовать стили десктопа.

А чтобы обеспечить поддержку сенсорных устройств на всех размерах экрана, мы используем для стилей **hover** специальные медиа запросы, это позволяет избавиться от проблем со стилями при взаимодействии с интерактивными элементами через тачскрин:

```css
@media (hover: hover) {
  .button_primary:not(.button_disabled):hover {
    border-color: var(--neutral-700);
  }
}
```

Так же на десктопе мы иногда скрываем некоторые элементы компонента, которые должны показываться по **hover** на сам компонент, и тогда на мобильном устройстве будет проблематично взаимодействовать с такими компонентами. В таком случае мы используем следующий медиа-запрос:

```css
@media (hover: hover) {
  .listStripe__controls {
    visibility: hidden;
  }
}
```

Это позволит скрывать элемент компонента только на устройствах, где доступен **hover**. Поэтому при разработке убедитесь, что все стили использующие **hover** обернуты специальными медиа-запросами и работают корректно на всех типах устройств.

## Запрещенные практики в CSS

- Использование `px`
- Использование `HEX` или `RGB` вместо переменных
- Использование `id` или атрибутов в качестве селекторов
- Глобальные `* {}` правила
- Использование `!important`
- Хардкодить размеры без необходимости
- Несоблюдение **БЭМ** методологии из этой документации
- Ссылаться в стилях компонента на блоки или элементы других компонентов
- Применять модификаторы к элементам
- Не оборачивать специальным медиа-запросом стили для Hover
- Стилизация компонента или элементов без использования тем или размеров

## Правила именования файлов и папок

### Правила camelCase для имен файлов:

- Стандартный camelCase: начинаются с маленькой буквы, могут содержать большие буквы в середине слова
- Запрещено использовать цифры в имени файла (например `selectbox2.tsx`)
- Запрещены точки в имени и другие спецсимволы
- Только буквы и цифры (без дефисов, подчеркиваний и т.д.)
- Файлы `.astro` в папке stories должен заканчиваться на "Story" (например: inputStory.astro)

_Исключением являются файлы шрифтов и конфигураций в корне проекта и некоторых других папках_

### Правила camelCase для имен папок:

- Стандартный camelCase: начинаются с маленькой буквы, могут содержать большие буквы в середине слова
- Разрешены квадратные скобки для динамических роутов

### Примеры правильных имен:

- ✅ myComponent.tsx
- ✅ [userId]/
- ✅ apiUtils/
- ✅ src/pages/stories/inputStory.astro

### Примеры неправильных имен:

- ❌ MyComponent.tsx (начинается с большой буквы)
- ❌ button2.tsx (содержит число в качестве итератора)
- ❌ user-service.tsx (содержит дефис)
- ❌ api_utils/ (папка содержит подчеркивание)
- ❌ [id].astro (имена файлов не могут быть в скобках)
- ❌ src/pages/stories/inputStories.astro (Файл заканчивается неправильно, Stories вместо Story)

### Исключения

- Исключенные папки: `node_modules, .git, .husky, .astro, .vscode, .idea, .github`
- Исключенные файлы: файлы конфигураций(package-lock.json и т.д.) или шрифтов (monserrat-light.woff2) для поддержки кеша шрифтов в браузере

### Скрипт проверки на pre-commit хуке

В проекте присутствует скрипт `pathCamelCaseChecker.ts`, который проверяет соответствие правилам для файлов и папок по путям: `src, utilities, scripts, features`. Скрипт проверки срабатывает только при коммите, для файлов, которые добавлены в индекс Git. В случае ошибки коммит сделан не будет, ошибки отображаются в консоли, либо в консоли Git, если работаете через IDE.
